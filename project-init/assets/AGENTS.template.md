# 项目协作规范（Agent 行为约束）

- 项目名称：{{PROJECT_NAME}}
- 技术栈：{{TECH_STACK}}
- 规范版本：{{VERSION}}
- 生效范围：本项目目录及全部子目录
- 约束对象：在本项目中工作的所有 AI Agent（Claude Code、ZCode、Cursor、Gemini CLI、Qwen Code、Windsurf、Cline、Copilot 等），无论以何种方式进入
- 优先级：用户当次的明确指令 > 本文件 > 各 Agent 的通用习惯。因用户指令偏离本规范时，须在对应日志中记一句偏离说明
- 修改本文件须经项目所有者确认

Agent 在本项目中执行任何读、写、创建、删除、移动或命令行操作之前，必须已完整阅读本文件并按其执行。

## 1. 目录职责与文件存放规则

```
<项目根>/
├── AGENTS.md                          本规范（所有 agent 规则文件的唯一内容来源）
├── README.md                          项目门面：简介与结构说明
├── CLAUDE.md / GEMINI.md / QWEN.md /
├── .cursor/ .windsurfrules / 等       各 agent 入口，内容仅指向本文件
├── docs/                              正式文档
│   ├── PRD.md / Design.md / TDD.md /
│   ├── 开发进度.md                    程序项目顶层文档（第 5 节）
│   ├── features/                      功能设计文档（一功能一文档）
│   ├── assets/                        文档配图等静态资源
│   ├── releases/                      交付物版本快照（第 2 节例外）
│   └── （其他交付物）
├── code/                              项目正式代码（含 tests/ 测试代码）
├── tmp/                               临时区：临时脚本、草稿、原始数据、中间输出（git 忽略）
└── .git/
```

1. 正式文件只能写入 `docs/`（文档类）或 `code/`（代码类）。项目根目录不得散落正式文件。
2. 一切临时产物——一次性脚本、抓取的原始数据、中间输出、试验性草稿——一律放 `tmp/`。临时脚本也是临时文件，不得放入 `code/`。
3. `tmp/` 中内容随时可清空。任何正式逻辑不得依赖 `tmp/` 中的文件；确需保留的内容必须"转正"——移入 `docs/` 或 `code/`，并按第 3 节记录日志。
4. 新建目录须有明确职责，禁止随手建目录；不再使用的空目录应删除。
5. 不确定文件归属时：与交付相关 → `docs/`；会被长期复用执行 → `code/`；其余 → `tmp/`。
6. `docs/assets/` 存放文档配图与静态资源，文件名以引用它的文档为前缀（如 `PRD-架构图.png`），便于溯源。
7. **命名规范**（适用于所有新建的文件与目录；`tmp/` 内可放宽，但也应能辨认来源）：
   - **见名知义**：名称直接表达内容与用途；禁止「新建文档」「未命名」「untitled」「aaa」「123」「doc1」等占位或无意义名称；
   - **字符集**：仅使用中文、英文字母、数字、连字符（-）、下划线（_）与扩展名点号；禁止空格及 `# % & { } < > * ? : " | ~ ! @ ^ + =` 等特殊字符，避免跨平台与命令行转义问题；
   - **不带时效与版本**：正式文件名不含日期与版本号（如 `2026-09-28-报告.md`、`报告_v2.md`）——时效由 git 与 .log.md 承担，版本由台账承担；唯一例外是 `docs/releases/` 交付快照（命名须含版本号）；
   - **语言惯例**：文档用中文名（与项目语言一致）；代码遵循所用语言的社区惯例（如 Python 模块 snake_case、测试文件 `test_*.py`、Web 组件 PascalCase）并全项目统一。

## 2. 文件修改规则

1. **就地迭代**：修改一律在原文件上进行。禁止生成 `xxx_v2`、`xxx_new`、`xxx_final`、`xxx_修改版`、`xxx_copy`、`xxx_备份` 等任何形式的版本副本文件。历史版本由 git 追踪，对比与回滚使用 `git diff` / `git checkout`。
2. **按版本迭代的是同一个文件**：内容演进时始终更新该文件本身，而不是另立新文件。确需拆分（结构上确属两个独立主题）时，先在日志中说明拆分理由再动手。
3. **重命名与移动**使用 git 感知方式（`git mv`），并在日志中记录去向；禁止静默删除或改名正式文件。
4. 修改前先确认 git 工作区状态；已存在未提交改动时，先向用户说明现状，避免把无关改动混入本次修改。
5. **交付快照例外**：已对外交付的成品可归档至 `docs/releases/`，命名含版本号（如 `v1.0-报告.docx`）。快照一经交付不再修改，因此豁免"禁版本副本"与日志要求；其后续演进仍在 `docs/` 原文件上就地迭代。

## 3. 修改日志规则（同名 .log.md 文件）

每个正式文件配一份同名修改日志，与文件同目录，逐条向下追加、不删改旧记录：

- 命名：`<主名>.log.md`。`docs/报告.md` → `docs/报告.log.md`；`docs/report.docx` → `docs/report.log.md`；`code/main.py` → `code/main.log.md`。
- 必须记录的时机：
  - 新建正式文件（首条记录写明文件用途）；
  - 对 `docs/` 下正式文件的每次实质修改；
  - `code/` 下影响结构、接口、依赖的修改（高频行级小改动可按日合并为一条；细节历史由 git commit 承担）；
  - 正式文件的重命名、移动、删除（记录去向与原因）。
- 无需日志：根目录的规范文件（AGENTS.md 及各 agent 入口）与 .gitignore；`docs/releases/` 下的交付快照（归档后不再修改）。
- 条目格式：

```
## 2026-09-28 14:30 — 创建
- 修改者：<agent 名称或"用户">
- 摘要：<改了什么>
- 原因：<为什么改，一句话>
```

## 4. 正式文件无 AI 痕迹

`docs/` 下所有交付内容与 `code/` 的注释中，禁止出现：

1. **对话腔**："作为一个AI""我是语言模型""希望对您有帮助""如果您需要我可以继续""接下来让我""让我们来看""祝您使用愉快"等；
2. **AI 声明与水印**：任何形式的"由 AI 生成/起草/润色"声明、水印、页眉页脚标注；
3. **emoji 与装饰符号**：正文（含标题、表格、图注）与代码注释不得使用 emoji；
4. **正文内修订记录**：正文中不得出现"修订历史 / 更新记录 / Changelog / 版本记录"章节——修订信息一律写入同名 `.log.md`（见第 3 节）；
5. **占位残留**："lorem ipsum""此处省略""待补充完整"等未完成占位（正式的 TODO 项除外，交付前应清零）。

文风基准：书面、正式、信息密度优先；结论先行，依据随后；枚举事实用表格或列表，不堆砌空话。

## 5. 程序项目开发流程（code/ 存在开发活动即适用）

### 5.1 顶层文档：缺一不可

| 文档 | 回答的问题 | 位置 |
|------|------------|------|
| PRD（产品需求文档） | 做什么、为什么做 | `docs/PRD.md` |
| Design Doc（设计文档） | 怎么做（整体方案） | `docs/Design.md` |
| TDD（技术设计文档） | 技术实现方案（选型、架构、测试策略） | `docs/TDD.md` |
| 开发进度台账 | 每个功能开发/测试/审核到哪一步 | `docs/开发进度.md` |

先文档后编码：开发任何功能前，相应文档须已建立并反映最新共识；需求或方案变化时，先改文档再改代码。
台账顶部维护「当前功能」一行，标明正在进行的功能与状态；任何 Agent 进入项目从这里接续，不得凭空另起炉灶。

### 5.2 一次只开发一个功能，测试与审核是门禁

1. **全部登记为待办**：收到需求时（哪怕一次列出多个功能），先把全部功能逐条登记进 `docs/开发进度.md` 的功能表，状态一律「待办」。未开发的功能不得提前动工，也不得从台账删除或省略登记。
2. **串行推进**：每次只从台账领取一个「待办」功能并同步「当前功能」行，状态流转：
   `待办 → 开发中 → 待测试（自测通过）→ 测试通过（验收测试通过）→ 已审核（人工确认）`
3. **测试门禁**：当前功能未通过验收测试，不得开始下一个功能，须先修复重测。测试未通过的问题逐条登记进台账「缺陷记录」表；该功能全部缺陷关闭并复测通过前，不得回到「测试通过」。用户明确指示跳过时，须在台账备注与本功能日志中记录该决定。
4. **审核门禁**：每个功能须经用户（或其指定审核人）测试确认并审核后，方可标记「已审核」。Agent 不得自行标记「测试通过」与「已审核」。
5. **台账即事实**：状态、测试结论、审核意见、缺陷记录的任何变化须实时同步回台账；台账与实际进度不符视为违规。
6. **测试代码**：功能测试代码属于正式代码，放 `code/tests/`，随功能一同开发与提交；禁止把测试脚本丢进 `tmp/` 或散落根目录。

### 5.3 功能设计文档（一功能一文档）

每个功能建一份以功能命名的解释文档 `docs/features/<功能名>.md`，开始开发该功能时同步创建，随开发、测试、审核进展回填：

```markdown
# <功能名>

- 状态：待办  <!-- 待办 / 开发中 / 待测试 / 测试通过 / 已审核 -->
- 关联：PRD 需求第 N 项 · 代码位置 code/...

## 1. 功能说明
做什么：功能描述、边界、明确不做什么。

## 2. 实现思路
怎么做：方案要点、关键决策及理由、依赖。

## 3. 测试情况
| # | 测试点 | 方法 / 用例 | 结果 |
|---|--------|-------------|------|
| 1 | <测试点> | <如何验证> | 通过 / 未通过 |

## 4. 审核记录
| 日期 | 审核人 | 结论 | 意见 |
|------|--------|------|------|
```

文件名默认用功能名；若所用工具链对非 ASCII 路径不兼容，可改用英文 slug 命名文件（如 `docs/features/export-report.md`），文档首行标题保留中文功能名，台账「设计文档」列登记实际路径。

## 6. git 约定

1. 正式修改完成后即提交。commit message 使用语义化前缀：`feat:`（新内容）、`fix:`（修正）、`docs:`（文档）、`refactor:`（重构）、`chore:`（杂务）。
2. `tmp/` 已被 .gitignore 忽略，不得用 `git add -f` 强行提交其中内容。
3. 收工自检：`git status` 中无未跟踪的正式文件；本次会话改动要么已提交，要么已向用户说明。

## 7. Agent 会话工作流

1. **进入项目**：先读本文件、`docs/开发进度.md`（从「当前功能」行接续）与 `git log --oneline -10`。
2. **工作**：按第 1–5 节存放与修改文件，逐次记日志；开发任务严格按第 5 节流程执行；临时产物随手进 `tmp/`。
3. **收工**：整理 commit → 运行巡检（project-init skill 的 check_project.py，可用时）→ 更新台账 → 向用户汇报：改了哪些文件、新增了哪些日志条目、当前功能状态、遗留了什么。
